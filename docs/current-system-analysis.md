## 2. データベースとテーブル構成

- **データベースは存在しない。** 永続化は **ファイルベース**（JSON / xlsx）のみ。
- 収集データの実質スキーマ（`results/<県>/<県>_emails.json` の1レコード）:

```json
{
  "facilityNumber": "2910103973",   // 事業所番号（10桁, 実質ユニークキー）
  "name":  "ジョブタス奈良三条通り事業所",  // 事業所名
  "corpName": "株式会社HSS",              // 法人名
  "address": "奈良県奈良市三条町472番地...",// 所在地
  "tel": "0742-81-4880",
  "fax": "0742-81-4881",
  "url": "https://www.jobtas.net/...",   // 事業所HP URL（任意）
  "email": "nara-sanjyo@jobtas-kansai.net",
  "status": "ok"   // ok / no_email_listed / error:...
}
```

- **重要:** `facilityNumber`（事業所番号）が **国が採番する一意キー**。重複判定の第一キーとして最適（仕様6.の「法人名・事業所名・電話・所在地・メール」判定より堅牢）。ただし複数サービス提供事業所で同番号が別レコードとして現れるケースがあるため、`facilityNumber` を主、`(名称+所在地)` を補助に用いる。
- 進捗管理: `results/all_progress.json` に県ごとの `{total, withEmail, complete}`。

## 15. 主なリスク

| リスク | 内容 | 対応方針 |
|------|------|------|
| 送信到達性・スパム判定 | 2万件規模の営業メール。ドメイン評価低下でブラックリスト入りの恐れ | SPF/DKIM/DMARC必須・個別送信・段階的増量（300→1,000→県単位）・配信停止・バウンス管理・suppression_list（横断）|
| 法令（特定電子メール法） | 未承諾の営業メール送信の適法性・オプトアウト義務 | 配信停止リンク必須・受信拒否の即時反映・出典明記・送信者情報明示。**送信可否は事業判断として要確認** |
| メールアドレスの取得経緯 | メールは難読化解除で取得したもの（サイト側の軽い自動収集対策） | 手順書の倫理方針を継承（出典明記・スパム目的に使わない）。**大量送信前に法務確認を推奨** |
| AI生成の事実誤り | 送迎・昼食・工賃・営業時間を根拠なく生成すると虚偽表示 | 未確認項目は「要確認」or 非表示。AIは事業所データ＋許可レイアウトのみ変更（ホワイトリスト）。公開前 人手確認必須 |
| 決済の二重処理 | Webhook 重複配信 | 署名検証＋イベントID冪等キー（`payments`/`lead_events` に unique 制約）|
| PII 保護 | 事業所連絡先の大量保有 | 最小保存・カード情報は自社非保存（決済代行のトークンのみ）・事業所間データ分離・監査ログ |
| コスト | HP生成/スクショ/AI編集/メールのランニング費用が件数比例 | 段階配信で流量制御。生成・スクショはジョブ化しレート制御 |
